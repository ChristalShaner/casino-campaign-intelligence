# Casino Campaign Intelligence

An end-to-end data engineering and analytics project that evaluates
casino promotional campaigns across two properties. The platform ingests campaign, visit, and redemption data; profiles and validates
the records; builds an assignment-grain analytical fact table; estimates
incremental campaign value using randomized offer and holdout groups;
stores the results in DuckDB; and presents findings in a Streamlit
dashboard.

## Project at a glance

  Area                           Implementation
  ------------------------------ -----------------------------------------
  Language                       Python 3.10
  Data processing                pandas
  Analytical database            DuckDB
  Transformation and reporting   Python and SQL

  Local orchestration            Python subprocess-based pipeline runner

### Key results

The current dataset contains 24,000 valid campaign assignments across
four campaigns and two casino properties.

  Measure                                                    Result
  -------------------------------------------------- --------------
  Clean assignments                                          24,000
  Clean visits                                               30,315
  Valid redemptions                                           4,965
  Incremental gaming revenue (stratified estimate)     \$227,664.39
  Promotional cost                                     \$110,000.00
  Incremental net value                                \$117,664.39
  Overall ROI                                               106.97%

The estimates are based on comparisons between randomized offer and
holdout groups within campaign, property, and player-segment strata. See
[methodology and assumptions](docs/methodology.md) before interpreting
the results.

## Business questions

The platform is designed to answer questions such as:

1.  Which campaigns generate the greatest incremental gaming revenue and
    net value?
2.  How do offer and holdout groups compare on response-period visit
    rates and gaming revenue per assigned player?
3.  Which campaigns have the strongest redemption rates?
4.  How do results vary by casino property and player segment?
5.  How much promotional spend is associated with the observed campaign
    outcomes?
6.  Which source-data quality issues could affect reporting or
    downstream analysis?

## Architecture

``` mermaid
flowchart TD
    A[Raw CSV files] --> B[Python profiling and validation]
    B --> C[Cleaning and quarantine]
    C --> D[Relationship validation]
    D --> E[Validated assignments, visits, redemptions]
    E --> F[Assignment-grain campaign fact]
    F --> G[Stratified incrementality analysis]
    G --> H[DuckDB warehouse]
    H --> I[SQL reporting mart]
    H --> J[Data quality tables]
    I --> K[Streamlit dashboard]
    J --> K
```

The project is organized into distinct stages:

-   **Raw data:** original CSV extracts are preserved under `data/raw/`.
-   **Validation and cleaning:** Python checks keys, duplicates,
    required values, and relationships. Excluded records are written to
    quarantine outputs rather than silently discarded.
-   **Analytical transformation:** visits and redemptions are summarized
    to the assignment grain while retaining the full cleaned assignment
    population.
-   **Incrementality:** offer and holdout outcomes are compared within
    campaign/property/segment strata.
-   **Warehouse and marts:** DuckDB stores cleaned facts, dimensions,
    analytical outputs, and data-quality reporting tables.
-   **Presentation:** Streamlit provides executive, campaign-analysis,
    and data-quality pages.

## Getting started

### 1. Requirements

-   Windows, macOS, or Linux
-   Python 3.10 or compatible
-   pip
-   The three source CSV files in `data/raw/`

### 2. Create and activate a virtual environment

**Windows PowerShell**

``` powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

**macOS / Linux**

``` bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

``` bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

The project uses pandas, DuckDB, Streamlit, Plotly, and pytest. Keep
`requirements.txt` aligned with the versions used by your environment.

### 4. Run the complete pipeline

From the repository root:

``` bash
python -m src.run_pipeline
```

The runner executes the automated tests and then runs the cleaning,
validation, transformation, analytics, warehouse, reporting-mart, and
data-quality loading stages in dependency order. It stops if a stage
returns a non-zero exit code.

Expected successful completion ends with:

``` text
PIPELINE COMPLETED SUCCESSFULLY
Completed steps: 13
Analytics warehouse is ready.
```

The exact runtime depends on the machine.

### 5. Launch the dashboard

After the pipeline completes:

``` bash
streamlit run dashboard/app.py
```

Streamlit prints a local URL, normally `http://localhost:8501`.

## Dashboard pages

1.  **Executive Overview** --- high-level campaign KPIs, incremental
    value, and campaign comparisons.
2.  **Campaign Analysis** --- campaign performance with
    campaign/property/segment filters and offer-versus-holdout

3.  **Data Quality & Pipeline Health** --- source-to-clean

## Automated tests

Run the full test suite independently:

``` bash
python -m pytest -v
```

The current suite contains 33 tests covering:

-   Duplicate and conflicting keys
-   Assignment group and offer-value rules
-   Missing player-segment handling
-   Negative gaming revenue and invalid promotional costs
-   Redemption relationship validation
-   Response-window boundaries
-   Stratified incrementality calculations
-   Missing or unmatched strata
-   ROI behavior when promotional cost is zero

## Important interpretation notes

-   The assignment population is the analytical denominator. Do not
    build campaign response metrics only from redeemed offers or
    visitors.
-   Gaming revenue may be negative and is retained. Promotional cost
    must be nonnegative.
-   Redemption rate is not the same as visit rate or campaign
    incrementality.
-   The 28-day pre-assignment period is descriptive baseline context; it
    does not replace the randomized holdout comparison.
-   The primary incremental-value estimate is stratified by campaign,
    property, and player segment.
-   One assignment with a missing player segment remains in the overall
    fact table but is excluded from the stratified estimate. This is why
    the overall stratified estimate includes 19,199 offer assignments
    rather than all 19,200.
-   The campaign SQL mart also displays direct offer-versus-holdout
    visit-rate differences. Those descriptive rates are not the same
    calculation as the stratified incremental-value estimate.
-   Quality issue counts are issue occurrences. A single record can
    generate more than one issue, so issue counts must not be
    interpreted as unique affected records.
-   The source extract is complete through October 31, 2026. The current
    assignment dates have complete 14-day response windows.

## Data and privacy

The project uses fictional/synthetic casino campaign data. Do not
replace it with real player-level or other sensitive data in a public
repository. Keep raw data, processed extracts, local database files,
credentials, and secrets out of version control unless you have explicit
authorization and an approved handling process.

## Known limitations and future enhancements

-   The pipeline is a local Python orchestrator, not a production
    scheduler.
-   Data quality checks and expected row counts are tailored to this
    challenge dataset; production pipelines should use configurable
    thresholds and source contracts.
-   The local DuckDB warehouse is designed for a single-user analytical
    workflow, not concurrent enterprise workloads.
-   Incrementality estimates would benefit from confidence intervals,
    statistical significance testing, and power analysis.
-   A production implementation could add structured logging, run
    metadata, retry policies, alerting, configuration management, and
    CI/CD.
-   Data lineage and schema-version tracking could be expanded.
-   Dashboard authentication and deployment controls would be required
    before exposing the app beyond a local environment.
